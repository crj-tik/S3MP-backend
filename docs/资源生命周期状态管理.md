# 账户、租户与应用生命周期

## 状态与访问边界

| 资源 | 可见状态 | 默认业务查询 | 删除后的处理 |
|---|---|---|---|
| 平台账户 | `active`、`disabled` | 排除 `deleted` | 账户会话、租户会话、成员关系和平台角色撤销 |
| 租户 | `active`、`suspended` | 只允许 `active` 数据面访问 | 成员、Principal、角色绑定、Key、存储和排队任务失效 |
| 应用 | `active`、`pending_takeover`、`suspended` | 排除 `deleted`；仅治理读取 `pending_takeover` | 应用 Principal 禁用、Key 撤销、授权版本递增 |

所有删除均为软删除，保留 UUID、删除时间、操作者和原因。普通查询不通过子资源 ID 暴露已删除父资源。

## 管理接口

- `DELETE /api/v1/platform/accounts/{user_id}`：软删除平台账户。
- `POST /api/v1/platform/accounts/{user_id}/restore`：恢复账户；邮箱或系统号发生冲突时返回 `409`。
- `DELETE /api/v1/platform/tenants/{tenant_id}`：软删除租户并在事务内撤销关联访问。
- `POST /api/v1/platform/tenants/{tenant_id}/restore`：恢复为 `suspended`，不会自动恢复已删除的子资源。
- `DELETE /api/v1/applications/{application_id}`：租户管理员或 Owner 软删除应用。
- `POST /api/v1/applications/{application_id}/restore`：恢复应用；必须存在 active 租户和 active Owner。

删除和恢复请求体统一为 `{ "reason": "..." }`。接口均记录平台或租户审计事件。

## 历史查询

平台账户和租户列表支持 `include_deleted=true`，但调用方必须同时拥有
`platform.audit.read`。历史结果只用于审计/清理，不能建立会话、签发 Key 或恢复数据面访问。

## 部署与回滚

1. 先执行 Alembic 迁移，再部署 API；迁移会扫描 active 身份重复并在发现冲突时中止。
2. API 部署后重启 worker，使其加载新的父级状态校验；不要在迁移未完成时开放删除接口。
3. 删除后的 S3 对象由既有清理任务异步处理；数据库状态提交失败时不触发外部删除。
4. 发现异常时可暂停清理 worker，保留数据库软删除状态；恢复操作必须经过管理权限和前置条件校验。
5. 迁移回滚前先停止新版本 API，并确认没有依赖部分唯一索引的身份复用数据。
