# 共享 S3 应用命名空间迁移盘点

## 当前模型

| 数据 | 当前归属 | 当前 provider 目标 | 新模型映射 |
|---|---|---|---|
| `storage_connection` | `tenant_id` | endpoint/region/bucket/path-style 由租户级记录提供 | 迁移为平台共享 profile 的历史证据；新写入只使用 active profile |
| `storage_space` | `tenant_id` | `bucket + root_prefix + storage_space_id` | 一对一绑定 `application_id`，成为应用逻辑命名空间 |
| `application` | `tenant_id` | 尚未绑定 storage space | 每个 active 应用分配稳定 `storage_namespace` |
| `file_object` | tenant + storage space | `provider_target_version` 和物理 key | 增加 application/namespace/profile 证据 |
| upload/multipart | tenant + storage space | session 中保存 provider target version | 增加 application/namespace/profile/reservation 证据 |
| ingestion/operation | tenant + storage space | 保存 bucket、relative key、physical key | 增加 application namespace 和迁移状态 |
| role binding | tenant + storage space + prefix | 用户/组/应用均可作为 principal | storage space 必须可反查 application |
| quota | tenant + storage space | used/reserved 以 space 为粒度 | 增加租户聚合和应用粒度 |

## 新 Key 规则

```text
active platform storage profile.bucket
  + immutable storage_space.storage_namespace
  + canonical application-relative key
```

推荐 namespace 形式为创建时分配的稳定 `tenant-slug/application-slug`；显示名称变更不得修改已分配 namespace。数据库同时保留 tenant_id/application_id，所有授权以 UUID 归属为准。

## 必须隔离的遗留情况

- 没有关联应用的 storage space
- 一个应用对应多个 active storage space
- 一个 storage space 对应多个应用
- 多租户/多应用共用旧 root prefix
- provider target version 为 0 或无法验证物理 key
- ingestion、upload、multipart、operation 只有旧 target 证据
- quota reservation 指向已删除或无法映射的 quota
- provider 中存在无法映射到唯一 tenant/application namespace 的对象

这些记录不能直接迁移成可用对象，必须进入审计/隔离流程。

## 隔离结果与兼容窗口

- 未能证明唯一 tenant/application 归属的旧记录写入 `provider_migration_manifest`，状态为 `pending_review` 或 `quarantined`；记录仅保存内部迁移证据，绝不通过文件、上传、分片或预签名接口返回。
- 应用存储空间、文件对象和延迟任务缺少 `application_id`、`storage_namespace` 或有效 profile version 时，运行时按 fail-closed 原则拒绝读取、签名和 provider 写操作；它们也不参与可用用量统计。
- `storage_connection.endpoint`、`region`、`path_style`、`credential_reference` 与 `storage_space.bucket`、`connection_id` 是只为迁移审计保留的兼容字段。新写入使用平台共享 profile，调用方不得用这些字段选择物理 Bucket、Region、Endpoint 或根路径。
- 兼容字段在当前迁移观察期内会保留在响应中并标记为 OpenAPI `deprecated`；观察期结束、迁移清单收敛且回滚窗口关闭后，才移除租户侧写入能力。

## 运维执行顺序

1. 运行 `python scripts/audit_shared_s3_namespace.py`，先处理所有冲突、孤儿和未映射记录；默认仅审计，不改 S3 对象。
2. 确认应用拥有稳定命名空间，并完成 provider migration manifest 的人工审核；任何不确定对象保持隔离。
3. 执行 `python scripts/reconcile_storage_quotas.py` 比对数据库可用文件与 quota 用量；只有审核差异后才使用 `--apply`。
4. 使用共享 profile 对新写入进行小范围上传、下载、预签名和跨应用拒绝测试；不可因为旧记录存在而回退到租户可选 Bucket/Endpoint。
