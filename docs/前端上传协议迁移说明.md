# 前端上传协议迁移说明

本项目的应用数据面只保留两种上传方式：直传和 Multipart 分片上传。两种方式都必须先通过 S3MP 完成路径、应用空间、权限、配额预留和幂等校验；应用不能自行拼接 Bucket、物理 Key 或 provider upload ID。

## 小文件：直传

1. 调用 `POST /api/v1/storage_spaces/{space_id}/direct_uploads`，请求体只提交相对路径、文件大小、Content-Type 和可选 checksum。
2. 响应返回上传会话 `id`、`status`、`expires_at`，以及短期 `url`、`method=PUT` 和 `headers`。
3. 应用使用响应中的 URL 以 `PUT` 发送原始文件二进制，必须带响应返回的 `Content-Type`。
4. 上传成功后调用 `POST /api/v1/direct_uploads/{upload_id}/completion`，S3MP 会重新检查对象大小、类型、checksum、权限和数据库入库状态。

应用不再提交 `direct_requested`，也不调用旧的 `/uploads/{id}/content` 代理上传接口。

## 大文件：Multipart

1. 调用 `POST /api/v1/storage_spaces/{space_id}/multipart_uploads` 创建会话。响应包含 `id`、`part_size`、`status` 和过期时间。
2. 按 `part_size` 切分原始文件，对每个分片调用 `PUT /api/v1/multipart_uploads/{multipart_id}/parts/{part_number}`，请求体是原始二进制，并带 `Content-Length`。
3. 服务端调用 provider 的 Multipart API 并保存真实 ETag；应用不得在请求体中伪造或确认 ETag。需要重试时使用同一个 `Idempotency-Key`。
4. 可调用 `GET /api/v1/multipart_uploads/{multipart_id}/parts` 查看服务端已确认的分片。
5. 调用 `POST /api/v1/multipart_uploads/{multipart_id}/completion`，提交有序的分片编号和服务端返回的 ETag。S3MP 会再次核对数据库记录、provider inventory、总长度和最终对象元数据。
6. 用户取消时调用 `DELETE /api/v1/multipart_uploads/{multipart_id}`；过期会话由服务端清理 provider upload 并进入可追踪的失败/待对账状态。

## 已删除的旧协议

- `proxy_upload_content`：不再由 S3MP 中转完整文件。
- `create_multipart_part`：不再只登记分片元数据。
- `confirm_multipart_part`：不再信任客户端单独提交的 ETag。
- `UploadCreate.direct_requested`：不再用布尔字段选择上传模式。
