## Why

当前配额实现能够记录租户和应用的使用量，但没有完整表达平台管理员“先给租户划总容量、再可选地从租户容量中划出应用独立容量”的业务规则。结果是未配置独立配额的应用、已划分应用的保留空间、共享剩余池之间缺少统一的可计算边界，平台无法安全地管理共享 Bucket 容量。

## What Changes

- 建立共享 Bucket → 租户总配额 → 应用独立预留配额 → 未分配应用共享池的容量层级。
- 增加平台级配额分配、调整、查询和应用配额撤销能力；租户成员仅可读取本租户的配额状态。
- 强制校验租户配额不超过 Bucket 容量，应用独立配额总和不超过租户配额。
- 将没有独立配额的应用纳入租户共享剩余池，并在直传、分片上传、完成、取消、过期和删除流程中保持租户总量与共享池的并发一致性。
- 明确应用独立配额的静态划分语义：应用未使用的已划分容量不会自动释放给共享池；撤销独立配额后才回到共享池。
- 补充配额状态、分配模式、剩余量、分配量和对账结果的契约字段及稳定枚举。
- 将存储空间级配额停止作为新业务模式；保留历史数据的读取和受控迁移策略，避免旧记录绕过新的租户/应用约束。

## Capabilities

### New Capabilities

- `tenant-application-quota-allocation`: 平台管理员对租户总池和应用独立预留容量进行分配、调整、撤销，并管理共享剩余池。

### Modified Capabilities

- `application-storage-quotas`: 修改配额层级、共享池计算、并发预留、生命周期状态和对账要求。
- `shared-s3-application-storage`: 增加共享 Bucket 容量上限、租户/应用命名空间容量统计和物理对象与逻辑配额的关联约束。

## Impact

- 影响治理领域的配额模型、服务、仓储、迁移和对账任务。
- 影响平台控制面配额 API、租户侧配额查询 API、OpenAPI 契约和元数据枚举目录。
- 影响文件直传、分片上传、完成、取消、过期清理和删除时的配额预留/结算逻辑。
- 需要配置共享 Bucket 容量上限，并补充 PostgreSQL 约束、行锁事务和跨租户/应用状态过滤。
- 需要为旧的 storage-space quota 记录定义迁移、只读兼容或明确隔离策略。
