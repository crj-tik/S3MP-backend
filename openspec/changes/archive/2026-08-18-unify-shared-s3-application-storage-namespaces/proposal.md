## Why

当前存储模型允许按租户和存储空间配置 Bucket/连接，但生产架构要求所有租户共用平台统一配置的 S3 Bucket 与 Region，并通过租户、应用和应用内路径实现隔离。现有模型还没有把应用命名空间、应用 API Key、用户组授权和配额统计闭合起来，容易造成跨租户/跨应用访问边界不清以及容量统计不准确。

## What Changes

- 新增平台级共享 S3 存储配置，统一管理 endpoint、region、bucket、path-style 和凭据引用；租户不再自行选择 Bucket 或 Region。
- 将逻辑存储空间与应用建立一对一绑定，形成稳定的租户/应用对象 Key 命名空间。
- 由后端根据租户和应用上下文推导最终 S3 Key，客户端只能提交应用内相对路径。
- 应用 API Key 只能访问所属租户的所属应用及其授权路径。
- 支持用户组作为授权主体，为组成员批量授予应用或应用内路径的读写、列举、删除和预签名权限；用户组不具备登录能力。
- 增加租户级和应用级容量配额、已用容量、预留容量及剩余容量统计，并在上传/分片上传创建阶段执行并发安全的容量预留。
- 统一文件、上传、分片上传、文件操作、预签名 URL 和后台 worker 的命名空间推导与授权校验。
- 为已有租户级连接/存储空间提供兼容迁移与明确的废弃策略，避免遗留数据绕过新的共享存储边界。
- 提供统一只读元数据目录，集中发布状态值、状态说明、允许流转、授权范围类型、授权效果、文件操作类型和配额范围，避免前端手写后端枚举。
- 将统一枚举目录落实为业务契约：领域枚举作为唯一来源，接口层使用强类型筛选参数，应用服务和领域层执行状态/范围校验，持久层将筛选转换为带租户与应用隔离的查询条件；目录同时声明每个枚举可用于的资源、字段和列表接口。
- **BREAKING** 不再允许租户通过管理接口指定任意 Bucket、Region 或跨应用物理前缀。

## Capabilities

### New Capabilities

- `shared-s3-application-storage`: 平台共享 S3 配置、租户/应用命名空间、统一对象 Key 推导和应用边界。
- `application-storage-quotas`: 租户与应用的配额、用量、预留和并发上传容量控制。

### Modified Capabilities

- `backend-identity-authorization`: 将用户组授权、应用主体授权和应用内路径范围纳入统一文件权限判断。
- `tenant-storage-isolation`: 将隔离边界从“租户/存储空间”扩展为“共享 Bucket/租户/应用命名空间”，并统一物理 Key 推导。
- `backend-file-storage`: 让文件、上传、分片、预签名和异步操作全部使用共享 Bucket 下的应用命名空间。
- `file-ingestion-provenance`: 让入库记录和异步清理保留应用命名空间及配额预留事实。

## Impact

- 影响存储连接/空间模型、应用模型、API Key 校验、角色绑定与用户组授权、配额模型、文件和 worker 服务。
- 影响 `/storage_connections`、`/storage_spaces`、应用文件操作、上传、分片上传、预签名 URL 及相关 OpenAPI DTO。
- 需要数据库迁移、旧存储配置迁移/只读兼容、统一 S3 初始化检查和新的容量统计任务。
- 需要前端改为管理应用存储空间、应用路径授权、用户组授权及配额信息，不再展示租户级 Bucket 配置。
- 需要前端从统一元数据目录获取展示标签和状态流转选项；权限目录和角色目录继续通过现有专用接口获取。
