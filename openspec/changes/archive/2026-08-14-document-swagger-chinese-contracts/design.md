## Context

The runtime schema currently supplies generated summaries but no operation descriptions, while the checked-in OpenAPI contract is the frontend source of truth. Repeating prose independently in route declarations and YAML would make terminology drift likely.

## Goals / Non-Goals

**Goals:**
- Define one documentation metadata source for operations and reusable concepts.
- Publish identical Chinese descriptions through runtime Swagger and the checked-in contract.
- Fail validation when a documented surface is incomplete or inconsistent.

**Non-Goals:**
- Change paths, payload structures, authorization behavior, or generated client types.
- Translate server logs, internal exception messages, or implementation-only symbols.

## Decisions

### 1. Use canonical reusable documentation metadata

Maintain operation descriptions and a field glossary in one backend-owned metadata module. Apply it to the runtime OpenAPI schema and materialize it into `contracts/openapi.yaml`. This makes one identifier mean one thing everywhere.

Alternative: write descriptions independently in every FastAPI route and OpenAPI YAML entry. Rejected because 80 operations and shared fields would drift.

### 2. Validate semantic documentation, not only paths and schemas

Extend the contract check to require Chinese descriptions for every public operation and every exposed parameter/property, and to compare runtime descriptions against the contract.

Alternative: rely on manual Swagger review. Rejected because missing descriptions are easy to reintroduce during future endpoint work.

### 4. Select the CSRF token by security domain, not cookie presence

The browser CSRF middleware SHALL classify the request before selecting the double-submit cookie. Account control-plane mutations, such as account logout and tenant-session selection, SHALL validate `s3mp_account_csrf`. Tenant-scoped mutations, including storage, file, permission, and group operations, SHALL validate `s3mp_csrf`. The presence of both session cookies is expected after tenant selection and MUST NOT make the account token win globally.

The local HTTP development profile SHALL allow `S3MP_BROWSER_COOKIE_SECURE=false`; HTTPS deployments SHALL retain `Secure` cookies. Swagger documentation SHALL state which cookie is readable and which header value must be sent for each security domain.

Alternative: choose the token by checking whether `s3mp_account_session` exists. Rejected because the account session remains active while a tenant session is selected, causing valid tenant writes to fail with `csrf_validation_failed`.

### 3. Preserve generated-schema structure

Documentation enrichment changes only descriptive OpenAPI metadata. Existing paths, security schemes, request validation, responses, and field names remain generated by the runtime and validated by the current compatibility check.

## Risks / Trade-offs

- [A new API bypasses the glossary] → Completeness validation fails the build.
- [A shared term needs a context-specific clarification] → Keep the canonical field description unchanged and add operation-level context instead.
- [Large generated contract diff is hard to review] → Keep metadata grouped by operation and reusable field names, then generate deterministic YAML changes.

## Migration Plan

1. Add metadata and runtime enrichment.
2. Materialize Chinese descriptions into the checked-in contract.
3. Add completeness and equality checks.
4. Rebuild the API container and verify `/docs` and `/openapi.json`.

Rollback removes enrichment metadata only; endpoints and payloads remain unchanged.
